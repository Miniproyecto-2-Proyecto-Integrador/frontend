# US-06 — Crear y visualizar salas propias

Rama: `feature/US-06-crear-visualizar-salas`.

## Implementación

- `/dashboard` conserva su ruta y muestra **Salas**, saludo, formulario y lista de salas propias.
- Sin salas, el estado vacío ofrece «Crear mi primera sala». Con salas, «Crear sala» y el icono + aparecen junto a Mis salas. El formulario solo aparece al solicitarlo, enfoca el nombre y permite cancelar con el botón o Esc, devolviendo el foco al activador.
- Crear sala valida el nombre recortado de 1 a 80 caracteres Unicode, igual que el backend. El nombre permanece si falla la solicitud. Mientras se crea se bloquea el envío; una referencia impide duplicar la petición por clics rápidos.
- Se usa `POST /api/salas` con `{ nombre }` y el ID token de Firebase. El servidor genera el ID, registra el propietario y responde con rol `administrador`.
- Después de crear se abre `/salas/:id`. Esta vista consulta `GET /api/salas` para confirmar que la sala pertenece a la cuenta actual; funciona también al recargar o abrir el enlace directamente. No confía en un rol enviado por el navegador.
- Las tarjetas muestran nombre, ID, rol, «Copiar ID» y entrada a la sala.
- La copia usa Clipboard API; el éxito se anuncia con `role="status"`. Si no se puede copiar, se explica cómo copiar manualmente el ID seleccionable.
- La lista distingue carga, error con reintento y lista vacía. Las respuestas de consultas anteriores se descartan al desmontarse o cambiar de cuenta.

## Integración existente

Se reutilizan `backend-api/src/routes/salas.routes.ts` y `backend-api/src/services/salas.service.ts`. No se modifican los backends, Firebase, las variables de entorno ni producción.

La vista interior de US-06 muestra la sala propia y el rol de administrador. El acceso como participante, la presencia por Socket.IO, el chat y los controles de audio y vídeo pertenecen a historias posteriores y no se implementan aquí.

## Comprobación

Ejecutado localmente: `npm run build`, `npm test` y `npm run lint`, con resultado satisfactorio.

Pendiente en navegador y aplicación publicada:

1. Con una cuenta sin salas: comprobar el estado vacío después de cargar.
2. Enviar nombre vacío, espacios y más de 80 caracteres: comprobar validación y ausencia de POST.
3. Crear una sala válida: comprobar 201, ID único, navegación a `/salas/:id` y rol administrador.
4. Recargar esa ruta y volver a Salas: comprobar persistencia y listado con nombre e ID.
5. Copiar ID: comprobar portapapeles y anuncio; probar permisos denegados.
6. Cambiar de cuenta: comprobar que la segunda cuenta no lista las salas de la primera.
7. Simular fallo de red: comprobar error, reintento y conservación del nombre.
8. Recorrer con teclado, lector de pantalla y tamaños de móvil; guardar evidencia en producción.

Estos pasos no se declaran ejecutados contra Render. El backend desplegado debe incluir las rutas GET y POST `/api/salas` que ya existen en el código local.

Compatibilidad de IDs: se aceptan las salas nuevas con códigos de ocho caracteres (letras, números, guion y guion bajo) y las existentes con IDs alfanuméricos de veinte caracteres. Desplegar primero frontend y realtime compatibles, después la API que genera códigos cortos.
