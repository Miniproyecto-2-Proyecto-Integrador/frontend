# US-02 — Google y finalización de perfil

Rama: feature/US-02-google-auth. Base: main, 701d61c.
Estado: implementación local probada de forma automatizada; verificación real
en navegador y Firebase pendiente. Sin commit, push, merge ni despliegue.

## Flujo

1. En /ingresar, Continuar con Google inicia signInWithPopup con
   GoogleAuthProvider desde el clic, sin esperar llamadas de red anteriores.
   Se solicita selección de cuenta y se bloquean operaciones duplicadas hasta
   terminar popup y consulta.
2. AuthProvider recibe el usuario y consulta GET /api/usuarios/yo con ID token.
   Se reutilizan la consulta coordinada y sus comprobaciones de identidad.
3. Un usuario Google con perfil confirmado navega automáticamente de /ingresar
   a /dashboard mediante Navigate con replace, únicamente al terminar la operación.
   Durante la consulta o ante errores no se redirige. La pantalla de éxito con
   Ir al Panel y Cerrar sesión permanece exclusivamente para el registro manual.
   /registro ya no ofrece el botón de Google; conserva sus redirecciones para
   sesiones Google que visiten esa ruta directamente.
4. Solo 404 significa perfil pendiente y dirige a /registro/usuario.
   Un fallo de red, 401, 500 o respuesta inválida muestra error y reintento.
   No se abre otro popup automáticamente y no se cierra la sesión por fallos.
5. La pantalla solicita nombres, apellidos, nombre de usuario y avatar.
   Valida al intentar guardar y revalida campos ya intentados durante edición.
6. Antes de guardar comprueba cuenta activa y consulta el perfil. Esto permite
   reconocer un perfil creado previamente cuando se perdió la respuesta.
   Si sigue pendiente, envía POST /api/usuarios y vuelve a consultar.
7. Solo después de confirmar el perfil permite ir al Panel. Si se abre la
   pantalla de finalización con un perfil completo, redirige al Panel.

## Datos y contrato

Contrato contrastado contra backend-api local, main 5cefd1b, en la fase de análisis.
No se modificaron archivos de backend ni se verificó una nueva versión desplegada.

- POST recibe únicamente nombres, apellidos, username y avatar, con Bearer token.
- Nombres/apellidos: obligatorios, máximo 50 caracteres después de trim.
- Username: ASCII, números o guion bajo, de 3 a 20; unicidad a cargo del backend.
- El frontend ofrece avatar1 a avatar6. El servidor admite texto hasta 300 caracteres.
- El correo viene del token; no se envía correo, contraseña ni tokens OAuth al cuerpo.
- Un 201 no devuelve perfil. GET devuelve success y data o 404 si no existe.
- El 409 se resuelve consultando de nuevo: perfil encontrado significa que ya
  se creó; otro 404 conserva el conflicto de nombre y su mensaje por campo.
- Una respuesta 200 con perfil incompleto es error. No existe endpoint de
  actualización: se muestra reintento/cambio de cuenta, sin intentar inventar uno.

## Identidad, estado y accesibilidad

Firebase sigue siendo la fuente de sesión. El contexto mantiene usuario,
perfil y estados; las páginas no crean otra sesión ni guardan tokens manualmente.
La operación de Google tiene solo un cerrojo de concurrencia y notifica sus
estados al contexto. La restauración usa el observador existente.

Se identifica una cuenta Google por providerData con google.com. Una identidad
con varios proveedores se considera Google si incluye ese proveedor; esta
historia no llama APIs de vinculación de cuentas.

displayName y email se muestran como referencia. No se deducen apellidos ni se
usan fotos externas como avatar. Nombres y apellidos quedan vacíos y editables.
Si falta el correo de la identidad, se explica el problema y se permite cambiar
de cuenta; no se habilita el guardado de un perfil potencialmente inválido.

Se reutilizan tarjetas, colores, tipografías, campos, radios y estados de US-01.
La pantalla enfoca su título al entrar; los errores de campo enfocan el primer
control y conservan aria-invalid/aria-describedby. Cancelar el popup se anuncia
como estado informativo; bloqueo/configuración/red se anuncian como error.
Los formularios no desaparecen durante reintentos del perfil.

La clave uid reinicia el formulario al cambiar la cuenta. Cambiar de cuenta
llama el cierre confirmado del contexto y vuelve a /ingresar, sin persistir
los datos escritos. Se descartan respuestas de consultas de otra cuenta.

## Protección y límites

- /dashboard conserva RequierePerfil. Carga, error y falta de perfil impiden
  mostrar contenido privado.
- Perfil Google pendiente: /registro/usuario.
- Perfil manual pendiente: /registro, conservando la recuperación de US-01.
- Sin sesión en /registro/usuario: /ingresar. Sesión manual allí: /registro.
- /ingresar solo implementa Google. El formulario de correo/contraseña, Panel
  real y protección general de /perfil y /salas/:id quedan
  para US-03. No se implementan salas.
- Si una cuenta cambia cuando un POST ya se envió, no es posible deshacer esa
  petición desde la interfaz. Se envía el token del usuario original y sus
  resultados se rechazan si ya no coincide la cuenta; no se mezclan perfiles.
- Los datos no guardados se conservan durante la sesión de edición, pero deben
  reintroducirse tras una recarga. Firebase sí restaura la autenticación.

## Cierre mínimo desde el Panel

El Panel conserva su presentación provisional y agrega únicamente Cerrar sesión.
No cambia el encabezado global ni implementa el resto de US-03.
La acción llama cerrarSesion de AuthProvider, el mismo mecanismo de US-01 que
espera signOut y confirma que Firebase ya no conserva un usuario.

La ruta monta Panel, que conserva RequierePerfil en su interior. Esto permite
mantener el controlador de cierre montado si el observador recibe null antes de
que resuelva la operación. Durante el cierre la guarda muestra solo Cargando:
no expone contenido privado ni monta una redirección prematura a /ingresar.
Después de la confirmación navega a /registro con replace. Fuera de ese intervalo,
las comprobaciones de sesión, carga, error y perfil pendiente no cambian.

cerrarDesdePanel solo orquesta la carga, el cerrojo y la navegación; no contiene
otra implementación de Firebase ni limpia la sesión por su cuenta. El bloqueo
se activa antes de esperar para evitar clics duplicados. Si falla, se libera,
la alerta recibe foco y se permite volver a pulsar Cerrar sesión.

## Ubicación acordada con UX

/ingresar es una pantalla mínima: título Iniciar sesión, acceso mediante
BotonGoogle, estados del contexto, reintento de consulta y enlace Crear cuenta.
No tiene formulario de correo/contraseña ni otra fuente de sesión.
Ante perfil pendiente manual conserva el retorno a /registro; para Google usa
/registro/usuario. La carga, la operación Google y el reintento bloquean
redirecciones hasta que termine la consulta.

BotonGoogle incorpora el logotipo multicolor mediante SVG inline, sin imágenes
externas ni dependencias. Se marca aria-hidden y focusable=false: el nombre
accesible procede del texto del botón. El registro manual ya no lo renderiza.
El cierre provisional del Panel y sus pruebas se conservan.

Se debe comprobar en navegador real el cambio de rutas, el aspecto del logotipo,
foco, teclado, popup y reintento a 390/1280 px. Las pruebas SSR verifican HTML,
pero no ejecutan efectos ni confirman navegación efectiva.
