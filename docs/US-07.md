# US-07 — Editar y eliminar salas

Rama: `feature/US-07-editar-eliminar-salas`. Consume `PATCH` y `DELETE /api/salas/:id` de `backend-api` (PR #11) y los eventos `sala:actualizada` y `sala:eliminada` de `backend-realtime`.

## Implementación

- Solo el anfitrión ve la tarjeta **Administrar sala** en `/salas/:id`. Quien entra como participante no ve los botones de editar ni eliminar; el rol lo calcula el servidor. Aunque alguien llamara directamente a la API, el servidor responde 403 y no cambia nada; el frontend muestra ese mensaje si ocurre.
- **Editar nombre:** formulario con el nombre actual seleccionado, validación de 1 a 80 caracteres Unicode (igual que el servidor), bloqueo de doble envío, estado de carga y mensaje de éxito anunciado con `role="status"`. Esc o «Cancelar» descartan el cambio y el foco vuelve a «Editar nombre». Los errores de la API aparecen en una alerta que recibe el foco y el nombre escrito se conserva.
- **Eliminar sala:** diálogo modal de confirmación crítica. El foco empieza en «Cancelar»; Esc o «Cancelar» cierran sin borrar y devuelven el foco al botón que lo abrió. Con la respuesta 200 se vuelve al panel con un aviso «La sala … se eliminó correctamente.» Si falla, el diálogo permanece abierto con el error.
- **Participantes conectados:** al abrir una sala se conecta Socket.IO (`auth.token` con el ID token vigente) y se entra con `sala:unir`. Si el anfitrión cambia el nombre, `sala:actualizada` lo refleja de inmediato en el título. Si elimina la sala, `sala:eliminada` devuelve a los participantes al panel con el aviso «El anfitrión eliminó la sala … Volviste al panel.» (`role="status"`). Al salir de la sala se envía `sala:salir` y se cierra la conexión.
- Si no hay conexión en tiempo real se muestra un aviso en la sala (sin bloquearla): los cambios hechos por la API siguen funcionando, pero conviene recargar para ver cambios de otras personas.
- **Lista del panel casi en vivo:** `/dashboard` vuelve a consultar `GET /api/salas` cada 20 segundos mientras la pestaña está visible y al volver a ella, sin pantalla de carga. Si la lista cambió (por ejemplo, la editaste o eliminaste desde otra pestaña o dispositivo) se actualiza sola y un anuncio oculto visualmente, con `role="status"`, avisa «La lista de salas se actualizó.» a los lectores de pantalla. Un fallo puntual de red conserva la lista que ya se ve y se reintenta en el siguiente ciclo. No se usa Socket.IO para esto: el servidor de tiempo real solo avisa a quienes están dentro de cada sala.
- Toda la información sale de la API y del servidor de tiempo real: el frontend no consulta Firestore.

## Integración existente

Se reutilizan `PATCH` y `DELETE /api/salas/:id` (backend-api, PR #11) y los eventos que emite la vigilancia de salas de `backend-realtime`. No se modifican los backends, Firebase ni las variables de entorno; el frontend usa `VITE_REALTIME_URL`. El chat, la presencia y los controles de audio y vídeo pertenecen a US-10 y posteriores: US-10 amplía el servicio de tiempo real creado aquí.

Despliegue: `CLIENT_ORIGINS` de `backend-realtime` debe incluir la URL del frontend en Vercel.

## Evidencia pendiente en producción

1. Con la cuenta A (anfitriona) crear una sala; con la cuenta B entrar con el ID y comprobar que no ve «Editar nombre» ni «Eliminar sala».
2. Cambiar el nombre desde A y comprobar que B lo ve actualizado sin recargar. Con el panel de A abierto en otra pestaña, comprobar que la lista cambia sola en unos 20 segundos (o al volver a esa pestaña) y que el lector de pantalla anuncia la actualización.
3. Dejar el nombre vacío o de más de 80 caracteres: comprobar el mensaje y que no se envía la petición.
4. Con B dentro de la sala, eliminar desde A: comprobar el aviso y el regreso de B al panel, y que A ve la confirmación.
5. Cancelar la eliminación con el botón y con Esc: comprobar que no se borra y que el foco vuelve al botón.
6. Intentar `PATCH`/`DELETE` con el token de B desde Swagger: comprobar el 403.
7. Cortar la red con la sala abierta: comprobar el aviso de conexión y la reconexión.
8. Recorrer el flujo con teclado y NVDA/VoiceOver; capturar Lighthouse (≥ 95) y versión móvil. Anexar al DUE y al PR.

Estas comprobaciones deben hacerse contra la API y el tiempo real publicados; no se presentan como ya realizadas.
