# US-04 — Ver y editar perfil

Rama: `feature/US-04-editar-perfil`.

## Implementación

La ruta privada `/perfil` abre en modo consulta, con campos y avatares desactivados. «Editar perfil» los habilita y muestra Guardar cambios/Cancelar. Guardar correctamente o cancelar vuelve a modo consulta; un error conserva la edición activa.

Muestra nombres, apellidos, usuario, correo y avatar de la sesión. Permite editar y guardar mediante `PATCH /api/usuarios/yo`, con el ID token de Firebase. Cancelar restaura los datos confirmados por la API. Los errores de disponibilidad se muestran junto a usuario/correo; los demás errores se anuncian como alertas. Los cambios guardados se anuncian con un mensaje de éxito.

Se validan campos obligatorios, longitudes, formato de usuario/correo y seis avatares permitidos. El servidor sigue siendo responsable de la unicidad. El formulario impide envíos duplicados y coordina el guardado con el cierre de sesión. Si se cambia el correo, se informa de la necesidad de iniciar sesión nuevamente con el correo actualizado.

Esta rama no implementa eliminación de cuenta (US-05) ni gestión de salas (US-06). La base visual son los cambios ya confirmados en `style/mejoras-visuales-home-auth`; integrar ese PR antes del PR de US-04 para que el diff contra main muestre solamente esta historia.

## Contrato contrastado con los backends

- `backend-api/src/index.ts` monta las rutas de usuarios bajo `/api`.
- `GET /api/usuarios/yo` devuelve `{ success: true, data: perfil }`.
- `PATCH /api/usuarios/yo` admite uno o varios campos: nombres, apellidos, username, avatar y correo. El frontend envía solamente los modificados y descarta UID, fechas y otros campos.
- El PATCH devuelve el perfil completo; el frontend comprueba su estructura antes de reemplazar el perfil de la sesión.
- Los errores 400/409 incluyen `message` y, cuando aplica, `errores` por campo.
- El 404 de un perfil inexistente devuelve exactamente `{ success: false, message: "Este usuario aún no tiene perfil." }`. Un 404 HTML o sin ese contrato se propaga como fallo de servidor y no inicia el registro.
- Cambiar únicamente username no envía correo ni obliga al backend a consultar o modificar Firebase Authentication.
- `backend-realtime` gestiona Socket.IO con `auth.token`; no interviene en consultar o editar perfiles.

Estos contratos fueron revisados en el código local. No confirman qué versión ejecuta Render. Un 404 de ruta al guardar requiere revisar el endpoint en la versión desplegada; cambiar el mensaje del frontend no publica ese endpoint.

## Comprobación local

```bash
npm run build
npm test
npm run lint
```

Las pruebas usan respuestas de API simuladas: validación, PATCH con token al perfil propio, errores de usuario/correo ocupado y bloqueo del formulario durante el guardado. La suite también revisa regresión de autenticación.

## Evidencia pendiente en producción

- Editar, guardar y recargar; comprobar persistencia de cada campo.
- Modificar sin guardar y cancelar; comprobar restauración de los datos guardados.
- Intentar un usuario/correo ocupado y comprobar los mensajes por campo.
- Cambiar correo y volver a ingresar con el nuevo.
- Probar fallo de red y reintento sin perder datos.
- Completar el flujo con teclado y NVDA/VoiceOver; comprobar foco y anuncios.
- Capturar versiones móvil/computador y Lighthouse; anexar al DUE y al PR.

Estas comprobaciones deben ejecutarse contra la API publicada; no se presentan como ya realizadas. Declarar la asistencia de IA en el PR o en la bitácora según los documentos del proyecto.
