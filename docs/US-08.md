# US-08 — Unirse a una sala

Rama: `feature/US-08-unirse-sala`. Consume el endpoint de `backend-api` integrado en el PR #10 (`GET /api/salas/:id`).

## Implementación

- El Panel (`/dashboard`) incluye la tarjeta **Unirme a una sala** con un campo «ID de la sala». Está siempre visible, también para quien aún no tiene salas propias.
- Antes de llamar a la API se valida el ID: vacío o solo espacios → «Escribe el ID de la sala.»; formato inválido → el mismo mensaje del servidor. Los espacios al inicio o al final se recortan (el servidor recibe el ID limpio). En ambos errores no se envía ninguna petición y el foco vuelve al campo.
- Con un ID válido se usa `GET /api/salas/:id` con el ID token de Firebase. Si la sala existe se abre `/salas/:id`; si no existe (404) se muestra el mensaje del servidor en una alerta que recibe el foco. Un fallo de red o un 401 no se presentan como «sala inexistente». Una referencia impide enviar dos veces con clics rápidos y se indica el estado de carga.
- `/salas/:id` consulta ahora esa misma ruta en lugar de listar las salas propias, así que sirve para anfitrión y participantes. El rol lo calcula el servidor (`administrador` o `participante`); el navegador no lo decide.
- **Acceso por enlace directo:** sin sesión, `RequierePerfil` envía al ingreso y, tras autenticarse, devuelve a `/salas/:id` (`destinoSeguro`). Con sesión se entra directamente.
- La vista muestra carga, error con reintento (red/servidor), «Sala no disponible» para 400/404 (sin reintento; el botón «Volver a mis salas» queda siempre visible) y, con éxito, nombre, rol y el ID con «Copiar ID».
- Toda la información sale de la API: el frontend no consulta Firestore.

## Integración existente

Se reutiliza `GET /api/salas/:id` de `backend-api` (PR #10). No se modifican los backends, Firebase ni las variables de entorno. La presencia en tiempo real, el chat y los controles de audio y vídeo pertenecen a historias posteriores y no se implementan aquí.

Además se revisó en navegador, con la API simulada, que los errores se anuncian y reciben foco, que `/salas/:id` funciona para anfitrión, participante, ID inexistente e ID inválido, y que axe (WCAG 2.2 A/AA y buenas prácticas) no reporta violaciones.

## Evidencia pendiente en producción

1. Con la cuenta A crear una sala; con la cuenta B pegar su ID (con y sin espacios alrededor) y comprobar que entra como participante.
2. Pegar un ID inexistente de 8 caracteres: comprobar el mensaje de sala no encontrada.
3. Dejar el campo vacío y escribir un ID demasiado corto: comprobar los mensajes y que no hay petición en la pestaña Red.
4. Abrir `/salas/:id` sin sesión: comprobar el ingreso y el regreso a la sala.
5. Abrir `/salas/:id` con una cuenta que aún no tiene perfil: comprobar que se pide completar el perfil.
6. Simular fallo de red: comprobar error y reintento.
7. Recorrer el flujo con teclado y NVDA/VoiceOver; capturar Lighthouse (≥ 95) y versión móvil. Anexar al DUE y al PR.

Estas comprobaciones deben hacerse contra la API publicada; no se presentan como ya realizadas.
